## 1. Osmose en détail

### 1.1 Comment j'ai vérifié

- `osmose.openstreetmap.fr` est **bloqué** par le proxy de l'environnement d'étude (curl : `CONNECT 403` ; WebFetch : domaine hors liste). **Aucun appel réel à l'API n'a donc été fait** : pas de réponse JSON observée, pas d'en-tête CORS observé, pas de mesure de délai.
- À la place, j'ai lu le **code source** des deux dépôts officiels (clonés le 10/11/2026) : [osm-fr/osmose-frontend](https://github.com/osm-fr/osmose-frontend) (commit `f8c5b04` du 29/10/2026, qui contient l'API) et [osm-fr/osmose-backend](https://github.com/osm-fr/osmose-backend) (commit `48bb59a` du 26/10/2026, qui contient les analyses). Ce que le code montre est **exact pour le code**, mais la configuration déployée (Apache devant l'appli, quotas éventuels) peut différer : à confirmer par un essai depuis un navigateur.
- Pages wiki lues : [Osmose](https://wiki.openstreetmap.org/wiki/Osmose), [FR:Osmose](https://wiki.openstreetmap.org/wiki/FR:Osmose), [Osmose/api/0.3](https://wiki.openstreetmap.org/wiki/Osmose/api/0.3).

### 1.2 L'API publique (version 0.3)

- **Version** : 0.3 est la version courante, 0.2 est dépréciée ([wiki Osmose](https://wiki.openstreetmap.org/wiki/Osmose)). Base : `https://osmose.openstreetmap.fr/api/0.3/`. Documentation OpenAPI générée par FastAPI à `https://osmose.openstreetmap.fr/api/docs` (lien donné par [Osmose/api/0.3](https://wiki.openstreetmap.org/wiki/Osmose/api/0.3)) ; le texte de cette doc est dans `api/app.py` du frontend.
- **Points d'entrée utiles** (routes lues dans `api/issues.py`, `api/issue.py`, `api/meta_0_3.py`, `api/false_positive.py`) :

| Route                                                                                         | Rôle                                                                                                                                        | Intérêt pour nous                                        |
| --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------- |
| `GET /0.3/issues?bbox=lon1,lat1,lon2,lat2&item=…&level=…&full=true`                           | Liste des signalements ouverts d'une zone                                                                                                   | Signalements d'une gare (emprise précalculée de l'index) |
| `GET /0.3/issues?osm_type=way&osm_id=…`                                                       | Signalements d'**un objet** OSM                                                                                                             | Boucle de contrôle après envoi (§ 1.5 b)                 |
| `GET /0.3/issues?username=…`                                                                  | Signalements dont l'utilisateur est le **dernier contributeur** de l'objet                                                                  | Suivi d'un testeur (hors appli)                          |
| `GET /0.3/issues.rss` / `.geojson` / `.csv` / `.josm` / `.gpx` / `.kml` / `maproulette.jsonl` | Mêmes filtres, autres formats                                                                                                               | RSS = abonnement des relecteurs sans rien développer     |
| `GET /0.3/issue/{uuid}`                                                                       | Détail : `lat`, `lon`, `uuid`, `title`, `subtitle`, `b_date`, `item`, `class`, `elems` (type, id, tags, corrections proposées), `new_elems` | Afficher le motif                                        |
| `GET /0.3/issue/{uuid}/done` · `GET /0.3/issue/{uuid}/false`                                  | Marque « corrigé » ou « faux positif »                                                                                                      | Voir § 1.5 c                                             |
| `GET /0.3/items`, `/0.3/items/{item}/class/{class}`, `/0.3/countries`, `/0.3/tags`            | Métadonnées, traductions                                                                                                                    | Libellés traduits (en-tête `Accept-Language`)            |

- **Paramètres** (dataclass `Params`, `modules/dependencies/commons_params.py`) : `bbox`, `item` (liste, ou `2xxx` pour une catégorie), `class` (avec un seul item), `level` (`1,2,3` par défaut), `status` (`open` par défaut, ou `done`, `false`), `username`, `country` (joker `france*`), `start_date`/`end_date`, `tags`, `fixable` (`online`/`josm`), `osm_type`+`osm_id`, `limit` (100 par défaut).
- **Champs renvoyés par `/issues`** : sans `full`, seulement `lat`, `lon`, `id` (uuid), `item`. Avec `full=true` : en plus `source`, `class`, `title`, `subtitle` (traduits), `level`, `update` (date de l'analyse), `usernames`, `osm_ids` (`{"nodes":[…],"ways":[…],"relations":[…]}`), `elems`.
- **Limites** : la doc dit « `limit` … 500 max » ([Osmose/api/0.3](https://wiki.openstreetmap.org/wiki/Osmose/api/0.3)), mais le code de `/issues` plafonne à 100 000 (`min(params.limit, 100000)`) : incohérence sans conséquence pour nous (une gare = quelques dizaines de signalements). **Aucun quota, aucune clé d'API, aucune condition d'utilisation publiée** n'a été trouvé (ni wiki, ni code). [non vérifié : existence d'une limitation au niveau du serveur web ; à demander à l'équipe Osmose].
- **CORS** : le code déclare `CORSMiddleware(allow_origins=["*"], allow_methods=["GET","POST","PUT","DELETE"])` (`api/app.py`). Un appel `fetch()` depuis `https://stationcomplete.org` est donc **autorisé par le code**. [non vérifié en conditions réelles : faire un `fetch` depuis la console d'un navigateur sur stationcomplete.org et vérifier l'en-tête `Access-Control-Allow-Origin`].
- **Disponibilité** : service bénévole d'OSM France, sans engagement de service publié [non vérifié : historique de disponibilité]. À traiter comme un service « bonus » qui peut manquer (§ 3).
- **Licence** : code GPL-3.0 (fichier `LICENSE` du frontend). **Aucune licence n'est publiée pour les signalements** eux-mêmes ([wiki Osmose](https://wiki.openstreetmap.org/wiki/Osmose), [FR:Osmose](https://wiki.openstreetmap.org/wiki/FR:Osmose) : « la page ne précise pas »). Ce sont des données dérivées d'OSM (tags et identifiants recopiés) ; afficher un signalement en citant « Osmose (OSM France) » ne pose pas de problème pratique, mais **la question est à poser** à l'équipe avant de redistribuer quoi que ce soit (par exemple dans l'index hebdomadaire).

**Ce qu'Osmose ne contrôle pas** (recherche dans tout le code backend) :

- **aucune analyse « quai qui croise une voie »** (`railway=platform` contre `railway=rail`) ;
- **aucune règle sur le schéma français des pancartes** (`FR:passenger_stop`, anciens `FR:ARRET_*`) : aucune occurrence dans `plugins/`, `analysers/` ni `mapcss/item_map.py`. Le dépôt [noeldev/FrenchRailwaySignalling](https://github.com/noeldev/FrenchRailwaySignalling) publie pourtant un fichier MapCSS **prévu pour JOSM et Osmose-QA** ([README, « JOSM Validator Rules »](https://github.com/noeldev/FrenchRailwaySignalling#josm-validator-rules) ; fichier [French_Railway_Signalling.validator.mapcss](https://noeldev.github.io/FrenchRailwaySignalling/French_Railway_Signalling.validator.mapcss)). Il n'est **pas encore intégré** à osmose-backend. → Correction à apporter à `docs/osm-tags-rapport.md` § 3.4, qui parle de « règles de validation JOSM/Osmose » comme si elles tournaient dans Osmose.
- **rien sur la cohérence quai ↔ voie** (`ref` du quai = `railway:track_ref` des voies longées) : c'est notre Q3, propre à stationcomplete.

### 1.4 Délai de mise à jour

- « Update are made each day » ([wiki Osmose](https://wiki.openstreetmap.org/wiki/Osmose)) ; « les analyses sont effectuées par région avec une fréquence de 1 à 2 jours » ([FR:Osmose](https://wiki.openstreetmap.org/wiki/FR:Osmose)). L'état réel par zone est publié sur `https://osmose.openstreetmap.fr/fr/control/update` **[non vérifié : page inaccessible ici]**.
- La France est découpée **par département** (`france_departement(...)` dans `osmose_config.py`, ex. `centre/cher`, `FR-18`) ; la Suisse **par canton** (`ch_part(...)`, ex. `geneva`, `CH-GE`), avec les analyses par défaut plus `osmosis_indoor`. La Suisse est donc couverte par le même Osmose (pas besoin d'un « Osmose suisse »).
- Conséquence : **Osmose ne peut pas valider un envoi en temps réel**. Un signalement créé par un envoi apparaît au mieux le lendemain, souvent 1 à 2 jours après. Un faux positif reste masqué tant que la version de l'objet ne change pas ([FR:Osmose](https://wiki.openstreetmap.org/wiki/FR:Osmose)).

### 1.5 Les quatre usages possibles, jugés

**(a) Afficher dans l'appli les signalements existants d'une gare.**

- Faisable techniquement : 1 requête `GET /api/0.3/issues?bbox=<emprise>&item=9015,1260,1040,1230,4090,2140&full=true` au chargement d'une gare, filtrée sur les objets que nous gérons (quais, voies longées, pancartes, `stop_area`).
- Intérêt réel **modeste** : nos quêtes Q3, Q5, Q7 couvrent déjà le principal (9015007/9015045 ≈ Q7, 9015037 ≈ Q5), et elles sont calculées sur des données fraîches, alors qu'Osmose a 1 à 2 jours de retard (un signalement déjà corrigé s'afficherait encore). Le reste (PTv2, angles, doublons) sort du périmètre « numéros, pancartes, quais » et demanderait des écrans et des textes nouveaux, traduits en 5 langues.
- Avis : **pas maintenant**. Mieux vaut **reprendre les règles** d'Osmose qui nous concernent dans le moteur de quêtes (code pur, frais, hors-ligne, sans tiers) — voir § 2.2. À reconsidérer seulement si l'équipe veut un avertissement « Osmose signale N problèmes dans cette gare → ouvrir Osmose » (un lien, sans appel réseau, coûte presque rien : voir § 3).

**(b) Après envoi, retrouver les signalements créés sur les objets modifiés.**

- C'est **l'usage le plus utile**, mais il ne doit **pas** se faire dans l'appli : l'appli est un éditeur, pas un outil de suivi, et ce suivi a lieu des jours plus tard.
- Hors appli, sans développement : Loïc et le relecteur s'abonnent au flux RSS `https://osmose.openstreetmap.fr/api/0.3/issues.rss?username=<pseudo testeur>&item=9015,1040,1230,1260,4090` (un par testeur du pilote), ou regardent la carte Osmose filtrée par utilisateur. Limite : `username` = **dernier contributeur** de l'objet ; si quelqu'un d'autre a retouché l'objet depuis, le signalement n'est plus rattaché au testeur.
- Plus tard, un petit script (hors appli, dans `scripts/`, lancé à la main) peut lister les objets des changesets `#stationcomplete` de la semaine (API OSM `changeset/#id/download`) puis interroger `/0.3/issues?osm_type=…&osm_id=…`. C'est de l'outillage de relecture, pas une fonction de l'appli. Attention : ce serait un appel en CI/script à un service autre que l'API OSM → à décider au regard de D4 (qui vise « ni dans l'appli ni en CI »).

**(c) Marquer un signalement corrigé ou faux positif depuis l'appli.**

- Le code montre que `GET /0.3/issue/{uuid}/done` et `/false` **ne demandent aucune authentification** (aucune dépendance d'utilisateur dans `status_uuid`, `api/issue.py` ; seul l'éditeur intégré d'Osmose demande la connexion OSM, [FR:Osmose](https://wiki.openstreetmap.org/wiki/FR:Osmose)). N'importe qui peut donc masquer un signalement.
- Avis : **ne pas le faire**. (1) « corrigé » est inutile : le signalement disparaît seul à l'analyse suivante si la correction est bonne ; (2) « faux positif » est un jugement d'expert qui masque le problème pour tous les autres contributeurs : le mettre dans les mains de débutants, depuis un téléphone, avec une requête `GET` non authentifiée, serait une source d'erreurs sans traçabilité ; (3) appel en écriture vers un tiers, contraire à l'esprit de D4.

**(d) Proposer à Osmose de nouvelles analyses propres aux gares.**

- C'est **la bonne façon** d'utiliser Osmose pour la qualité des gares : les contrôles tournent chez Osmose sur toute la France (et la Suisse), pour tous les contributeurs (iD, JOSM, StreetComplete…), pas seulement ceux de stationcomplete, et l'appli ne dépend de rien.
- Comment contribuer ([CONTRIBUTING.md](https://github.com/osm-fr/osmose-backend/blob/master/CONTRIBUTING.md), [doc/2-PluginMapCSS.md](https://github.com/osm-fr/osmose-backend/blob/master/doc/2-PluginMapCSS.md)) : **ouvrir d'abord un ticket** sur [osmose-backend/issues](https://github.com/osm-fr/osmose-backend/issues) — « PRs introducing new analyzers without a prior issue will not be accepted. This applies especially to AI-generated code » ; analyses en **MapCSS** (règles par objet, partagées avec JOSM), en **Python** (plugins) ou en **SQL/PostGIS** (analyses géométriques entre objets) ; tests `pytest` obligatoires (`sax`, `lint`, `mypy`) ; traductions via Transifex ; contact `osmose-contact@openstreetmap.fr`, salon Matrix `#osm-osmose:matrix.org` ([wiki Osmose](https://wiki.openstreetmap.org/wiki/Osmose)).
- Propositions concrètes, par ordre de facilité :
  1. **Intégrer le MapCSS français des pancartes** (noeldev) comme plugin `only_for = ['FR']`, sur le modèle exact de `Josm_openrailwaymap` (fichier Python généré depuis une URL MapCSS). Effort côté Osmose faible, le fichier existe déjà et embarque ses auto-tests. Bénéfice : anciennes valeurs `FR:ARRET_*` et valeurs non documentées signalées partout.
  2. **Règles MapCSS simples** à proposer à OpenRailwayMap (donc reprises automatiquement par Osmose via 9015) ou en plugin : `railway:track_ref` posé sur autre chose qu'une voie ; `railway=platform` avec `railway:track_ref` (existe : 9015008) ; `local_ref` sans `ref` sur un quai ferroviaire [à discuter : usage réel à mesurer avec taginfo].
  3. **Analyse SQL** (plus lourde, à discuter avec l'équipe) : quai (`railway=platform`, surface) qui **croise ou recouvre** une voie `railway=rail` sans `layer`/`level` différent ; deux voies longeant des quais de la même gare avec le même `railway:track_ref` (notre Q7 « numéro en double »).

### 2.2 Contrôles avant envoi, dans l'appli : peut-on embarquer un validateur ?

- **Validations d'iD** (licence ISC, compatible GPL ; [modules/validations](https://github.com/openstreetmap/iD/tree/develop/modules/validations), commit `5b81398` du 03/11/2026) : `crossing_ways`, `close_nodes`, `mismatched_geometry`, `outdated_tags`, `missing_tag`, `missing_role`, `almost_junction`, `osm_api_limits`… Elles importent le graphe d'iD (`coreGraph`, `coreTree`), ses actions (`actionMergeNodes`, `actionSplit`…), `presetManager`, le traducteur et d3. **Ce n'est pas une bibliothèque réutilisable** : l'embarquer reviendrait à embarquer une bonne partie d'iD, incompatible avec le budget JS. De plus `crossing_ways` **ignore les surfaces ferroviaires** (« don't check railway or waterway areas ») : il ne verrait pas un quai qui chevauche une voie. On peut en revanche **reprendre les algorithmes** (ISC : en gardant la mention de copyright).
- **Données de tags d'iD** : `@openstreetmap/id-tagging-schema` 7.3.0 (ISC, vérifié sur npm). Son `deprecated.min.json` fait 36 ko (6,1 ko gzip, mesuré) pour 499 règles, dont `railway=platform` seul → ajouter `public_transport=platform`. **Bonne nouvelle** : les quais dessinés par l'appli portent déjà `railway=platform` + `public_transport=platform` + `train=yes` (`src/routes/gare/dessiner/+page.svelte`). Embarquer ce fichier ne servirait qu'à signaler des tags hérités sur des objets que l'appli ne crée pas : faible intérêt.
- **Évaluer du MapCSS en JavaScript** : je n'ai trouvé **aucune bibliothèque JS légère et maintenue** qui exécute des règles de validation MapCSS de JOSM [non vérifié de façon exhaustive]. Écrire un interpréteur MapCSS serait disproportionné.
- **Recommandation (APPLI)** : écrire les contrôles nécessaires **à la main, dans le cœur métier en TypeScript pur** (`src/lib/core/`), comme `checkShape` et le moteur de quêtes, et **reprendre comme tests unitaires les exemples `assertMatch` / `assertNoMatch`** des règles MapCSS d'OpenRailwayMap et de noeldev (ils sont recopiés dans les plugins Osmose générés). Coût en poids : quelques centaines d'octets. Contrôles proposés, appliqués à l'état « après envoi » de chaque objet touché :
  1. **Tags** : `ref` / `local_ref` / `railway:track_ref` sans doublon ni espace autour de `;` (Osmose 3060) ; pas de mot « voie », « quai », « track » dans ces valeurs (Osmose 9015009/9015010) ; `railway:track_ref` posé uniquement sur une voie (9015008) ; aucune valeur `FR:ARRET_*` écrite ; valeurs de pancartes limitées aux valeurs documentées du schéma français (liste à extraire de `rules.json` de noeldev) ; `railway:signal:direction` présent (9015037).
  2. **Géométrie** : déjà fait par `checkShape` (côtés qui se croisent, croisement des voies, chevauchement des quais). À ajouter : pas deux sommets consécutifs à moins de 0,2 m (≈ `close_nodes` d'iD), pas d'angle quasi nul (≈ Osmose 1190), pas de nœud orphelin sans tag après une suppression (≈ Osmose 1080/1140).
  3. **Relations** : pas de membre en double (Osmose 1040/3), pas de relation vidée (déjà refusé).
  - Un contrôle qui échoue **bloque** l'envoi de la saisie concernée (« À revoir »), avec un texte clair ; pas d'envoi « quand même ».

### 3.2 Pourquoi ne pas intégrer Osmose dans l'appli aujourd'hui

1. **Doublon partiel** : les classes Osmose les plus pertinentes (9015007, 9015045, 9015037) recoupent Q5 et Q7, calculées sur des données fraîches.
2. **Décalage temporel** : 1 à 2 jours de retard ; l'appli montrerait des problèmes déjà corrigés, y compris par l'utilisateur lui-même la veille. C'est une source de confusion pour des débutants.
3. **Coût de décision** : révision de D4, nouvelle origine CSP, nouveau tiers dans les mentions de vie privée (§ 7.6), licence des signalements à clarifier, textes à traduire en 5 langues.
4. **Exigence « pas de solution provisoire »** : une intégration « pour voir » qu'on retirerait ensuite serait du provisoire. Mieux vaut décider une fois, après le pilote, avec des chiffres (combien de signalements Osmose sur les gares du pilote, combien hors de nos quêtes).

## 4. Recommandation finale

### 4.1 En 10 lignes

1. Osmose est un bon conseil, mais **pour relire les données après coup, pas pour valider un envoi** : ses analyses ont 1 à 2 jours de retard (par département en France, par canton en Suisse).
2. **Maintenant, sans toucher à l'appli** : Loïc et le relecteur suivent les envois avec OSMCha (filtres `editor=stationcomplete`, suppressions, commentés, « Review requested », en RSS) et Osmose (RSS par testeur, items 9015/1040/1230/1260/4090).
3. **Maintenant, dans l'appli (QA-0)** : poser `host=https://stationcomplete.org` (annoncé mais absent du code), aligner `imagery_used`, mettre à jour la grille du relecteur (elle dit encore « aucune suppression ») et ajouter la révocation (osm-revert) au plan d'incident.
4. **Ensuite (QA-2)** : des contrôles locaux avant envoi en TypeScript pur (tags, géométrie, relations), inspirés des règles d'Osmose, d'OpenRailwayMap et d'iD, testés avec leurs exemples. Pas de réseau, pas de poids notable.
5. **Ensuite (QA-3 à QA-5)** : case « Je souhaite une relecture » (`review_requested`), signal des commentaires sur mes envois, Notes OSM rédigées par l'utilisateur : tout passe par l'API OSM, donc **D4 reste intact**.
6. **Côté communauté (QA-6)** : proposer à l'équipe Osmose d'intégrer le MapCSS français des pancartes (déjà prévu pour Osmose, pas encore intégré) puis une analyse « quai qui croise une voie » ; c'est le meilleur levier, car il profite à tous les éditeurs.
7. **Plus tard, après le pilote (QA-7)** : décider, chiffres en main, si l'appli affiche les signalements Osmose ; si oui, réviser explicitement D4, ajouter l'origine à la CSP, ne transmettre que la bbox.
8. **Ne pas faire** : marquer « corrigé » ou « faux positif » depuis l'appli (requête non authentifiée qui masque le problème pour tous), appeler taginfo ou Overpass depuis l'appli, embarquer les validations d'iD (trop liées à iD), créer des notes automatiques.
9. **Ne pas utiliser** Keep Right (données arrêtées depuis janvier 2026) ; le Code de conduite des modifications automatisées ne s'applique pas tant que chaque modification est revue à l'écran.
10. Questions ouvertes : voir § 4.2 ; ce qui n'a pas pu être vérifié (API Osmose en direct, CORS réel, page de mise à jour) est marqué **[non vérifié]**.
